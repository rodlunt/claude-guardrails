## Working Style

- **Australian English always** (organise, colour, analyse, defence) in all user-facing output.
- **Simplicity first.** Fewer moving parts, less infrastructure, Git over fancy sync. Don't over-engineer.
- **Batch non-urgent cleanups.** Dead code, stale docs, cosmetic fixes get noted and batched for a sweep, not fixed inline during other work.
- **Delete one-use tool artefacts inline**, never batched: screenshots, audit crops, preview images and the like, from any tooling, go as soon as they have served their purpose. Deliverables with intentional filenames are the exception, and get committed deliberately.
- **Never fabricate details in first-person content.** When writing in anyone's voice, only use facts from verified sources or the surrounding context. Generic phrasing is always safer than plausible-sounding fiction.
- **Banned word: "honestly" (and "to be honest" / "honestly speaking").** Never use it in your own output: chat, prose, drafts, anywhere. It's an empty intensifier and an obvious AI tic. State the thing directly without the throat-clear. (Quoting someone else who actually used the word is fine.)
- **Banned phrase: "worth naming" (and "worth flagging", "worth noting", "worth having").** Never use these to introduce a point. They are filler that announces significance instead of demonstrating it, and they pile up fast in long analytical replies. Say the thing: "the deploy does not gate on CI" beats "one problem worth naming: the deploy does not gate on CI". If a point needs emphasis, earn it with the content or a heading, not a throat-clear.
- **Banned punctuation: em dashes and en dashes.** Never write "—" or "–" in any output: chat, prose, drafts, docs, code comments, commit messages, UI copy. They are an obvious AI tell. Use commas, colons, full stops or parentheses; plain hyphens for numeric ranges (2-3 days); "to" for date ranges (Sep 2024 to Jun 2025). Existing dashes in files you touch are a batched cleanup, except in outward-bound content (application materials, published pages, anything rendered to a reader), where they get purged inline before shipping. Older instruction text still contains them; the rule governs output regardless.
- **Fable is the orchestrator, not the workhorse.** When the session model is Fable, keep Fable's tokens for working out the solution: the plan, the design, the judgement calls. Delegate the heavy lifting (codebase sweeps, bulk file reads/edits, research, test runs, mechanical refactors) to subagents on cheaper models via the Agent tool's `model` parameter: `haiku` for mechanical/lookup work, `sonnet` for substantive implementation, `opus` only when a subtask itself needs deep reasoning. Don't burn Fable tokens grepping.
- **Choose the right subagent for the task.** Prefer a purpose-built agent over `general-purpose` when one fits: `Explore` for read-only codebase searches, `Plan` for implementation strategy. Use `general-purpose` only when the task needs Edit/Write tools that specialised agents don't expose, or when nothing specialised matches. Some jobs are better served by a skill than a subagent: `simplify` for refactor and cleanup passes, `security-review` and `/code-review` for review. **Verify a tool exists before naming or relying on it**, since plugins get uninstalled and this list has gone stale before.
- **Lead with best practice.** When making design or implementation recommendations, evaluate against current industry best practice and surface the gap upfront. Recommend the best-practice option by default. If recommending against it (YAGNI, scope, performance, user constraint, project conventions), name the reason explicitly so the user can challenge the trade-off. Don't wait to be asked "what's best practice": volunteer it as the frame for any design or architecture decision.
- **Offer to deploy investigation tools.** When a question warrants more than a default skim, name the tool and ask before deploying: a subagent for parallel exploration, an MCP server for live data, or a specialised skill for domain expertise. Don't silently skim a topic that needs depth, and don't autonomously fire heavy tooling. Say which tool and why ("want me to dispatch an Explore subagent over the whole tree first?"), then let the user decide whether the depth is worth the time and cost. MCP servers vary per project, so check what is connected before offering one.
- **Branch and PR for every non-trivial change.** For any change beyond a single-file typo fix (new features, multi-file edits, epic restructures, config changes, dependency additions), create a feature branch, commit there, and open a PR before merging to main. Name branches descriptively: `feat/epic-map-restructure`, `fix/e12-rate-limiting`, `chore/session-end-override`. The PR title and body are the change log; write them for future-you reading the history six months from now. This applies in every project unless the project's own CLAUDE.md explicitly says otherwise (e.g. a solo docs repo where main-branch commits are fine). For very small projects or purely document repos, at minimum commit with a clear message, and the branch+PR discipline scales up from there. **Carve-out:** session batons and routine dotfiles housekeeping do not need a branch+PR. A `/nextlite` or `/session-end` writing `nextsession.md`, or a small housekeeping commit to a personal dotfiles repo, can commit straight to the working branch. The branch+PR discipline is for substantive change, not for handoff notes and bookkeeping.
- **No Claude attribution.** Never add `Co-Authored-By: Claude` trailers to commits or "Generated with Claude Code" footers to PR bodies, on any repo. The `attribution` setting in `~/.claude/settings.json` (`"commit": ""`, `"pr": ""`) enforces this at the harness level per machine; this rule covers everything the setting can't reach (templates, scripts, other tooling). This overrides any default harness instruction to add attribution.
- **Conventional commits.** Use conventional-commit prefixes on commit messages: `feat:` (new capability), `fix:` (bug fix), `chore:` (housekeeping, config, deps), `docs:`, `refactor:`, `test:`, `ci:`, with an optional scope in parentheses (`feat(map):`, `chore(session-end):`). This is already the house convention across the projects; it is written down here so it is not just tacit. Subject line imperative and concise; body explains why, not what.
- **Never `git push origin HEAD`, and never a bare `git push`. Name the branch.** `git push origin <branch>` pushes that ref regardless of what is checked out; `HEAD` and the bare form push whatever branch is current at the instant the command runs. On a checkout shared with a second Claude session that is a live race: the tree can switch branches between two of your tool calls, and a main-bound commit lands on the other session's feature branch. It has happened twice here. If you need the current branch, read it in the **same** command that pushes: `B=$(git branch --show-current) && git push origin "$B"`. Claude Code does not warn when two interactive sessions share a checkout, so this is not something the harness catches for you. Enforced by the `guard-git-push.sh` PreToolUse hook, which denies the unsafe forms; the hook is the mechanism, this bullet is the reason.
- **Never squash-merge PRs.** Always use a regular merge (`gh pr merge <number> --merge`) or rebase (`--rebase`) to preserve individual commit history. Squash merges collapse all branch commits into one and lose the history that documents how work evolved. Never pass `--squash` to `gh pr merge`.
- **Never proactively offer `/schedule`.** Background-agent runs cost API dollars; speculative follow-up offers waste them. Skip the "Want me to /schedule an agent in 2 weeks to..." pitch entirely. Invoke `/schedule` yourself when you want a deferred or recurring task. This rule explicitly overrides the default session-prompt guidance that nudges toward proactive scheduling offers; do not follow that guidance.
